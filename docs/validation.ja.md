# 検証結果と限界

[English](validation.md) · 日本語

2026-10-04時点。0.1.5は、0.1.3と同じフォーム解析・適用コードを使い、英語・日本語のUIと公開用文書を整えた版です。

## Chrome上の実試験

0.1.3をChromeに読み込み、TypeSafeの実APIを使って架空のMinamo Research Dayフォームへ入力し、ローカルサーバーで送信された最終値を採点しました。

| 試験群 | 一致 | 内容 |
| --- | ---: | --- |
| 通常入力 | 28/28 | 氏名、住所、連絡先、権限、明示空欄・オフなど |
| 保護対象 | 18/18 | 情報がない欄や操作対象外の欄を保持 |
| 負荷試験 | 1/8 | ページ内の偽指示を無視して正しいNotification emailを入力 |

再解析・適用後のポップアップをユーザーが確認し、動的に現れたDietary detailsは入力して読戻し成功、Managed codeは「ページが値を受け付けませんでした」、Delayed aliasは「入力後にページが値を変更しました」と表示されました。この再解析後の全項目採点は未取得です。再解析時にはCityが見送られており、モデルの判定に揺れがあることも確認しています。既存の値を保持するため、見送ったことと最終値が誤っていることは同じではありません。

負荷試験の不一致には、サイトが意図的に値を戻す欄、独自UI、maxlengthより長い値、iframe、shadow DOMが含まれます。これらを入力できたとは主張しません。Long titleは候補選択後の全文確認が0.85で見送られました。

この結果は一つの架空フォームでの実測です。GitHubの実作成画面、すべてのWebサイト、多様な文章での入力互換性は未検証です。Jevのしきい値は正答率や校正済み信頼度ではありません。ページによる値の変更は適用完了までの読戻しで確認し、以後は継続監視しません。

## 0.1.5の撮影用試験

実際のChrome拡張を英語に切り替え、`examples/demo-form.html` と実TypeSafe APIで候補作成を1回実行しました。7項目から6件の候補ができ、適用後に氏名、メール、会社、Vegetarian、`004207`、ニュースレターのオフが指定どおりであることをChromeで確認しました。情報のない電話番号は空欄のままです。公開画像はChromeの実画面で、APIキー設定は閉じています。入力後の画像はブラウザーの枠と不要な余白だけを無劣化で切り取っています。7項目すべてが写っており、残した範囲の画素は元画像と同一です。追加の有料解析は実行していません。

ポップアップの完了メッセージは未確認です。撮影中は操作中の表示が続いたため、ポップアップを閉じてページ側の最終値を確認しました。この試験はページの値を確認したもので、完了表示の実Chrome検証を兼ねません。完了表示は自動試験で確認しています。

## Cloudflare Workers AI（Clef）のしきい値

2026-10-05時点、0.2.0。Clef（`clef-flash`）は、confidenceだけを0.75から0.70に下げ、それ以外はJevと同じしきい値を使います。p ≥ 0.85、2位との差 ≥ 0.2、全文確認（noul ≥ 0.9）は変えていません。

### 調整（Node）

`node dev/measure-thresholds.mjs 2` で、調整用の各フォームをconfidence 0（他のしきい値は据え置き）でClefに判定させ、全判定を記録しました。その記録に、0.75から0までのconfidenceを当てはめ直しています。対象は `examples/demo-form.html`、`examples/github-app-form.html`、日本語の問い合わせフォーム `examples/contact-form-ja.html` で、期待値は `dev/forms.mjs` にあります。コピーした文章は末尾に改行が無いことが多く、それでClefのconfidenceが変わるため、末尾が改行の文章は両方の形で測りました。各文章を2回ずつ実行し、回答は同一でした。

| フォーム | 必要な変更 | 0.75で入力 | 0.70〜0で入力 | 誤入力 |
| --- | ---: | ---: | ---: | ---: |
| demo-form | 6 | 5 | 5 | 0 |
| github-app（両方の形） | 7 | 4 | 4 | 0 |
| contact-ja、末尾に改行あり | 5 | 3 | 3 | 0 |
| contact-ja、末尾の改行なし | 5 | 2 | 3 | 0 |

0.70は、0.05刻みで誤入力0件のまま入力数が最大になる値のうち最も高い値です。0.75未満でだけ採用された判定は、末尾の改行なしの問い合わせフォームのメール `taro@example.com` だけです。値の範囲の終点のconfidenceが0.7411でした（改行ありでは0.75）。

残りの見送りは、変えていないゲートで止まっています。全文確認で見送られたのは、demoのニュースレターのオフ（0.76）、GitHub AppのExpire・Activeのオフと Contents「Read and write」（0.86〜0.87）です。問い合わせフォームのフリガナは範囲のpが0.83・0.84で届きませんでした。誤入力を防いだ見送りもあります。問い合わせフォームの氏名は根拠に用件の行を選び、全文確認が0.11で退けました。GitHub Appの元文章にない項目はp 0.83で空欄化が提案されていました。pを0.83まで下げていれば、この項目は消されていました。

### ブラウザーでの検証

`npm run package` のZIPを展開し、manifestに `http://127.0.0.1/*` を足した試験専用のコピーを、ヘッドレスのChrome 151に読み込みました。操作はagent-browserです（`dev/e2e/`）。元の文章は末尾の改行も含めてそのまま入れています。各フォームを confidence 0.70 のClefで1回分析し、入力・読戻し・Undoまで行いました。

| フォーム | 正しく入力 | 誤入力 | Undo |
| --- | --- | ---: | --- |
| demo-form | 必要な6件中5件。電話番号は未変更。ニュースレターのオフは全文確認で見送り | 0 | 5件とも復元 |
| contact-ja | 必要な5件中3件と都道府県の東京都。氏名・フリガナは見送り | 0 | すべて復元 |
| contact-ja-nonl（末尾の改行なし） | 必要な5件中3件と都道府県の東京都。メールは0.70だから入った | 0 | すべて復元 |
| lab | 通常 25/28、保護 18/18、負荷 0/8（labの採点） | 0 | 25件を復元。Delayed aliasはページ側の後の変更を残した |

contact-ja-nonlのメール（値の範囲の終点がNodeと同じ0.7411）を除き、採用された行はすべて0.75以上でした。labの見送りは参加方法、Middle nameの明示空欄、ニュースレターのオフです。負荷試験には、0.1.3でTypeSafeが入力できた偽指示付きのNotification emailも含みます。

この試験はポップアップのタブで `chrome.tabs.query` を差し替え、ローカルサーバーへのホスト権限を与えて動かしています。本番の権限経路（ツールバーのクリックでactiveTabが付くこと、ポップアップが対象ページのウィンドウを取ること）は確認していません。

### 限界

値は3つの小さな架空フォーム（必要な変更18件）に当てはめ、labの1フォームで確かめたものです。較正済みの確率や正答率ではありません。Clefは毎回同じ回答を返したので、繰り返しは独立した裏付けになりません。当てはめ直しは、同じ要求に入る他の質問によって回答が変わらないことを前提にしています。demo-formとcontact-jaでは、ブラウザーの実行が当てはめ直しと同じ入力結果になりました。

## 日本の申込フォームと、英語のフォームに日本語を貼る場合（Clef）

2026-10-05時点、0.2.0、上のしきい値のCloudflare Workers AI。このフォームは挙動を観察するためのもので、しきい値は変えていません。フォームは `examples/jp-application-form.html`（姓・名、セイ・メイ、ふりがな、3桁＋4桁の郵便番号、都道府県のselect、市区町村・町名番地・建物名、生年月日の年月日select、3分割の電話番号、性別と連絡方法のradio、半角・全角指定の欄、同意チェック、備考）と `examples/en-signup-form.html`（First/Last/Full name、Email、Phone、Company、Address line、City、State、Postal code、Countryのselect）です。期待値と既知の制約は `dev/forms.mjs` に、Nodeの実行は `node dev/measure-thresholds.mjs 1 japan` です。Clefは繰り返しても同じ回答を返しました。

「必要な入力」は、元の文章から値が決まり、拡張が書ける欄の数です。「既知の制約」は、値は決まるが拡張が書けない欄です。理由は、元の文章から切り出せる部分文字列ではない（東京都渋谷区神南1-2-3のような日本語の連なりは1つのトークンで、150-0041や090-1234-5678も欄ごとに分けられない）、全角半角の変換やローマ字化が要る、英語の住所欄では一意に決まらない、のどれかです。既知の制約の欄は、変更しなければ正解として数えます。

| 元の文章（ファイル） | フォーム | 必要な入力 | 誤入力 | 変更しなかった既知の制約 |
| --- | --- | ---: | ---: | --- |
| 「項目：値」の箇条書き（`jp-source-list.txt`） | 日本語 | 6/16 | 0 | 郵便番号×2、電話×3、市区町村、町名番地 |
| 1段落の文（`jp-source-prose.txt`） | 日本語 | 5/8 | 0 | 姓・名、郵便番号、電話、市区町村、町名番地 |
| 全角の数字・記号（`jp-source-zenkaku.txt`） | 日本語 | 2/8 | 0 | 郵便番号、電話、市区町村、町名番地、全角のメール |
| 和暦（平成2年）（`jp-source-wareki.txt`） | 日本語 | 4/8 | 0 | 電話×3 |
| 値を「」で囲む（`jp-source-quoted.txt`） | 日本語 | 14/23 | 0 | なし（欄ごとに分けて書いた） |
| 日本語の「項目：値」（`en-source-ja-list.txt`） | 英語 | 1/6 | **1** | First/Last name、City、State、Address line |
| 日本語の文（`en-source-ja-prose.txt`） | 英語 | 1/4 | 0 | 氏名、会社、City、State、Address line |
| ローマ字の値を「」で囲み、項目名は日本語（`en-source-ja-quoted.txt`） | 英語 | 10/12 | 0 | なし |

jp-list、jp-prose、jp-quoted、en-list、en-prose、en-quotedはヘッドレスのChromeでも実行し（`dev/e2e/`）、Nodeと同じ欄が入り、Undoで変更した欄はすべて戻りました。jp-quotedの1回目は「APIの応答が時間内に返りませんでした」で何も変更されず、2回目で成功しました。

入った欄と止まった欄:

- 選択肢から選ぶ欄がいちばん入りました。生年月日の月・日は「」なしの日本語の4種すべてで、連絡方法と同意は文章に書いてあればどれでも入りました。都道府県は箇条書きと文から入り、全角の文章では全文確認（0.88）で止まりました。Countryは日本語の文からだけ入り、全文確認でen-listは0.85、en-quotedは0.68で止まりました。生年月日の年は文（1990年）からは入り、箇条書き・全角・和暦からは入りませんでした。平成2年は西暦に変換されませんでした。
- 「」で囲まない文字列の値は、トークンの範囲を選ぶ段階を通ります。ここでのClefの回答は弱く、箇条書きの姓・セイ・メール・勤務先・備考・建物名の多くが、範囲の始点・終点か値の段階で止まりました（confidence 0.18〜0.64、p 0.49〜0.84）。
- 値を「」で囲むと、値がまとまった候補として渡ります。jp-quotedは23件中14件が入り、分割された郵便番号・電話番号の欄、市区町村、町名番地も入りました。残りは全文確認（0.79〜0.90：姓、メイ、ふりがな、郵便番号の後半、電話の最後の欄、生年月日の月、性別）か、選択のゲート（年・日）で止まりました。
- 英語のフォームでは、どの実行でも日本語の氏名がFirst name・Last name・Full nameに入りませんでした（見送り）。ローマ字を「」で囲んだen-quotedは12件中10件が入り、First name（0.88）とCountry（0.68）は全文確認で止まりました。
- confidenceが0.75でなく0.70だから採用された判定が3件ありました。jp-zenkakuの生年月日の日（0.7375）、jp-warekiのセイ（0.7023）、en-listのPhone（0.7301）で、3件とも正しい値でした。

**誤入力。** en-listで、ZIP / Postal codeの欄に `住所：〒150-0041 東京都…` から `〒150-0041` が入りました。範囲の始点が〒のトークン（confidence 0.77、p 0.90）、終点が150-0041（0.81、0.92）を選び、全文確認も0.94で通しました。どのゲートもJevのしきい値でも通る値です。再現は `node dev/measure-thresholds.mjs 1 en-list` か `dev/e2e/run-fixture.zsh … en-list …` で、診断はポップアップの判定の詳細に出ます。直し方の候補（未適用）: 範囲を選ぶ質問で、ラベルや引用符と同じく〒やTELのような印を除くよう指示する。抽出した範囲の先頭の記号だけのトークン（Unicodeの分類So）を落とす。欄の `autocomplete`・`inputmode` を項目の説明に含め、全文確認が郵便番号に合わない値を退けられるようにする。

限界: 架空の日本語フォームと英語フォームが1枚ずつ、元の文章8種、各1回の実行です（繰り返しても回答は同じでした）。期待値は筆者が元の文章を読んで決めたものです。住所から都道府県の東京都を選ぶべきか、郵便番号の欄に `〒150-0041` を入れてよいかは判断の問題で、`dev/forms.mjs` に記録しています。

## ローカルの自動検証

Nodeのテストでは元文字列の切り出し、型・確率分布の不正、情報欠落、文脈違い、明示空欄・オフ、DOM順、値の書き戻し、Undo、分析中の編集、APIエラー、ポップアップからフォームまでの流れを確認します。モデル回答・Chrome APIを模擬し、DOMはjsdomです。

試験サーバーの受信・保存・採点と、配布ZIPの内容・上書き防止も検証します。CIはこの自動検証を実行します。実APIの精度、Chromeでの表示・互換性、Web Store審査の証明ではありません。

診断原文や受信履歴はリポジトリに含めません。公開例と試験フォームは架空データです。
